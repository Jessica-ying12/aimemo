# 方案规划完整流程

## Step 1: 需求澄清

在写方案前，先回答这些问题：

```markdown
## 需求澄清

### 做什么
- 一句话描述功能：___
- 用户场景：用户在什么情况下使用这个功能？
- 预期结果：用户操作后看到什么？

### 不做什么（明确边界）
- 本次不包含：___
- 后续版本再做：___

### 依赖什么
- 需要哪些已有模块？
- 需要新增哪些依赖库？
- 需要新的数据库表吗？
- 需要新的 IPC 接口吗？
```

## Step 2: 技术方案

```markdown
## 技术方案

### 架构决策
- 数据存储方案：___（SQLite 新表 / 已有表扩展 / 文件系统）
- 前后端分工：___（哪些逻辑在主进程，哪些在渲染进程）
- 第三方依赖：___（需要新增什么库，为什么选它）

### 数据流
用户操作 → 渲染进程 → IPC → 主进程 → 数据库/API → 返回

### 涉及文件（预估）
- 新增文件：___
- 修改文件：___

### 风险点
- 可能遇到的问题：___
- 降级方案：___
```

## Step 3: 拆解为 commit 列表

按照 [commit-splitting.md](commit-splitting.md) 的规则拆解。

输出格式：

```markdown
## Commit 列表

| 序号 | 标题 | 类型 | 依赖 |
|------|------|------|------|
| 1 | 新增 xxx 数据库表 | feat(db) | 无 |
| 2 | 实现 xxx 服务层 | feat(module) | #1 |
| 3 | 注册 IPC 接口 | feat(ipc) | #2 |
| 4 | 实现 xxx 页面 UI | feat(ui) | #3 |
| 5 | 添加单元测试 | test(module) | #2 |
```

## Step 4: 可行性审查

按照 [feasibility-review.md](feasibility-review.md) 逐项检查。

## Step 5: 生成任务文件

按照 [task-file-template.md](task-file-template.md) 为每个 commit 生成独立的 md 文件。

存放位置：`docx/tasks/{version}/NNN-{name}.md`

---

## 方案文档存放

```
docx/
├── tasks/           ← 可执行的任务文件（最终产物）
├── proposals/       ← 方案文档（规划阶段产物）
│   ├── 001-feature-name.md
│   ├── 002-feature-name.md
│   └── ...
└── ...
```

方案文档是过程产物，任务文件是最终产物。方案通过审查后才生成任务文件。
