# 任务文件标准模板

## 文件位置

```
docx/tasks/{version}/NNN-{name}.md
```

- version: v0.1, v0.2, ..., v1.0, v1.1, ...
- NNN: 三位数字，版本内递增
- name: 2-4 个英文单词，kebab-case

## 完整模板

````markdown
# [NNN] 任务标题（中文，简洁描述做什么）

## 前置依赖
- v{X.Y}/NNN（列出所有必须先完成的任务）
- 如果无依赖写：无

## 背景
用 2-3 句话说明为什么要做这个。不要写废话，只写对执行者有用的上下文。

## 目标
用 bullet points 列出这个 commit 完成后的状态：
- 具体产出 1
- 具体产出 2
- 具体产出 3

## 具体步骤

### 1. 步骤标题

说明 + 代码：

```typescript
// 完整的、可直接复制使用的代码
// 不要省略 import 语句
// 不要用 "..." 省略关键逻辑
```

### 2. 步骤标题

```typescript
// 更多代码
```

### 3. 步骤标题（如果需要修改已有文件）

在 `path/to/file.ts` 中添加/修改：

```typescript
// 明确标注是"添加"还是"替换"
// 如果是修改，给出足够的上下文让执行者能定位到修改位置
```

## 验证方式
- 具体的验证步骤 1（如：`pnpm dev` 启动后看到 xxx）
- 具体的验证步骤 2（如：在 DevTools 中执行 xxx，返回 xxx）
- 具体的验证步骤 3（如：`pnpm test` 通过）

## Commit Message
```
type(scope): description in english
```
````

---

## 模板使用规则

### 代码片段要求

| 要求 | 原因 |
|------|------|
| 包含完整 import 语句 | 执行者不需要猜测从哪里导入 |
| 不用 `...` 省略核心逻辑 | 执行者不需要自己补全 |
| 标注文件路径 | 执行者知道代码写在哪里 |
| 如果修改已有文件，给出上下文 | 执行者能定位到修改位置 |

### 验证方式要求

| 要求 | 原因 |
|------|------|
| 可执行的命令 | 不是"确认功能正常"这种模糊描述 |
| 预期结果 | 执行者知道什么算"通过" |
| 覆盖 happy path | 至少验证正常流程 |

### 前置依赖要求

| 要求 | 原因 |
|------|------|
| 精确到任务编号 | 不是"完成 V0.1"这种模糊依赖 |
| 只列直接依赖 | 不列传递依赖（A 依赖 B，B 依赖 C，A 只写依赖 B） |

## 示例：好的任务文件

```markdown
# [003] 文件监控服务

## 前置依赖
- v0.2/001（采集器基类）

## 背景
需要实时监控 AI 工具的对话目录变化，使用 chokidar 比原生 fs.watch 更可靠。

## 目标
- chokidar 文件监控服务实现
- 支持启动/停止/重启
- 文件写入完成后才触发回调

## 具体步骤

### 1. 安装依赖

\`\`\`bash
pnpm add chokidar
\`\`\`

### 2. 创建 electron/services/collector/watcher.ts

\`\`\`typescript
import chokidar, { FSWatcher } from 'chokidar';
// ... 完整代码
\`\`\`

## 验证方式
- 创建一个测试目录，启动 watcher 监控
- 在目录中创建文件，确认日志输出 "File add: ..."
- 停止 watcher 后创建文件，确认不再触发

## Commit Message
\`\`\`
feat(collector): implement file watcher service with chokidar
\`\`\`
```

## 反例：坏的任务文件

```markdown
# 添加功能

## 步骤
1. 创建文件
2. 写代码
3. 测试

## 验证
确认功能正常
```

问题：
- 没有前置依赖
- 没有背景
- 步骤没有代码
- 验证不具体
- 没有 commit message
