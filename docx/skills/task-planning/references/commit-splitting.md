# Commit 拆分规则

## 拆分原则

### 必须遵守

1. **每个 commit 后 `pnpm dev` 能正常启动** — 不能有编译错误
2. **每个 commit 只做一件事** — 一个 commit 不能同时加表 + 写服务 + 写 UI
3. **不能有前向引用** — commit A 不能 import commit B 才创建的文件
4. **测试独立** — 测试 commit 可以单独存在，不依赖后续 commit

### 建议遵守

5. **后端先于前端** — 先有数据和接口，再有 UI
6. **基础设施先于业务** — 先有框架/抽象，再有具体实现
7. **核心路径先于边缘情况** — 先跑通 happy path，再处理异常

---

## 拆分模式

### 模式 A：新增功能模块

```
1. 数据库迁移（新表）
2. 数据库 CRUD 操作
3. 业务服务层逻辑
4. IPC 接口注册
5. 前端页面 UI
6. 单元测试
```

### 模式 B：修改已有功能

```
1. 数据库迁移（加字段/加表）
2. 修改服务层逻辑
3. 修改/新增 IPC 接口
4. 修改前端 UI
5. 更新测试
```

### 模式 C：纯前端功能

```
1. 创建组件
2. 接入数据（store / api 调用）
3. 交互逻辑（事件处理、状态切换）
```

### 模式 D：纯后端/基础设施

```
1. 安装依赖 + 配置
2. 核心逻辑实现
3. 注册到系统（IPC / 生命周期钩子）
4. 测试
```

---

## 粒度判断

### 太大了（需要继续拆）

- 一个 commit 改动超过 300 行
- 一个 commit 涉及 3 个以上不相关的文件
- 一个 commit 的描述需要用 "和" 连接两个动作
- 验证步骤超过 5 个

### 太小了（可以合并）

- 只改了一行配置
- 只加了一个 import
- 两个 commit 必须一起才能验证

### 刚好的粒度

- 一个 commit = 一个可验证的功能点
- 改动 50-200 行
- 验证步骤 2-4 个
- commit message 一句话能说清

---

## 依赖关系标注

每个 commit 必须标注它依赖哪些前置 commit：

```
依赖: 无                    ← 可以独立执行
依赖: #1                   ← 必须先完成 #1
依赖: #1, #2               ← 必须先完成 #1 和 #2
依赖: v0.2/005             ← 依赖其他版本的任务
```

**禁止循环依赖：** A 依赖 B，B 不能依赖 A。

## 命名规范

文件名：`NNN-kebab-case-description.md`

- NNN：三位数字编号（001, 002, ...）
- 描述：用 2-4 个英文单词概括

示例：
```
001-add-chat-table.md
002-chat-crud-service.md
003-chat-ipc-handlers.md
004-chat-page-ui.md
005-chat-unit-tests.md
```

## 常见错误

| 错误 | 正确做法 |
|------|---------|
| 一个 commit 里既建表又写 UI | 拆成：建表 → 服务层 → IPC → UI |
| commit 里引用了还没创建的文件 | 调整顺序，被引用的先创建 |
| 测试和实现放一个 commit | 可以放一起（如果改动不大），也可以分开 |
| commit message 写 "update code" | 写具体做了什么：`feat(db): add chat_sessions table` |
| 一个 commit 安装 5 个不相关的依赖 | 按用途分批安装，或在第一个使用处安装 |
