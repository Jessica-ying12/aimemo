# 方案修正流程

## 何时需要修正

审查发现以下问题时需要修正：

| 问题类型 | 严重程度 | 处理方式 |
|---------|---------|---------|
| 依赖顺序错误 | 阻塞 | 调整 commit 顺序 |
| 缺少前置步骤 | 阻塞 | 插入新 commit |
| 代码无法编译 | 阻塞 | 修正代码片段 |
| 依赖库不兼容 | 阻塞 | 更换技术方案 |
| 缺少错误处理 | 重要 | 补充到对应 commit |
| 缺少测试 | 重要 | 追加测试 commit |
| 性能问题 | 一般 | 追加优化 commit |
| 命名不规范 | 一般 | 修正命名 |

---

## 修正步骤

### 1. 定位问题

明确是哪个 commit 有问题，问题的根因是什么。

```
问题：Commit #3 引用了 utils/validators.ts，但该文件在 #5 才创建
根因：拆分时遗漏了 validators 的创建步骤
```

### 2. 确定修正方案

| 根因 | 修正方案 |
|------|---------|
| 顺序错误 | 交换 commit 顺序（确认交换后不产生新的依赖问题） |
| 遗漏步骤 | 在正确位置插入新 commit（重新编号） |
| 代码错误 | 直接修正任务文件中的代码片段 |
| 技术方案不可行 | 回到 Step 2 重新设计，可能需要重新拆分 |

### 3. 执行修正

#### 调整顺序

```
修正前：001 → 002 → 003 → 004
问题：003 依赖 004 的内容
修正后：001 → 002 → 004(改为003) → 003(改为004)
```

重新编号所有受影响的文件。

#### 插入新 commit

```
修正前：001 → 002 → 003
问题：002 和 003 之间缺少一个创建工具函数的步骤
修正后：001 → 002 → 002b(新) → 003

最终重新编号：001 → 002 → 003(新) → 004(原003)
```

#### 修正代码

直接编辑任务文件中的代码片段。修正后需要重新审查该 commit 及其后续 commit。

### 4. 重新审查

修正后必须重新走一遍 [feasibility-review.md](feasibility-review.md)，确认：
- 修正没有引入新问题
- 所有依赖链仍然正确
- 编号连续无跳跃

## 修正记录

每次修正记录在方案文档底部：

```markdown
## 修正记录

### 修正 1 (2026-06-05)
- **问题：** Commit #3 引用未创建的 validators.ts
- **修正：** 将 validators.ts 的创建从 #5 移到 #2b，重新编号
- **影响范围：** #3-#6 重新编号为 #4-#7

### 修正 2 (2026-06-05)
- **问题：** 缺少 @eslint/js 依赖
- **修正：** 在 002 的依赖安装步骤中补充
- **影响范围：** 仅 #2
```

## 常见修正场景

### 场景 1：发现需要新的数据库表

```
原计划：直接在服务层 commit 中建表
修正：拆出独立的"数据库迁移" commit，放在服务层之前
```

### 场景 2：发现依赖库不兼容

```
原计划：使用 library-A
修正：
1. 评估替代方案（library-B, library-C, 自己实现）
2. 选择替代方案
3. 更新所有引用该库的 commit
4. 重新审查
```

### 场景 3：发现功能范围过大

```
原计划：一个版本完成全部功能
修正：
1. 识别 MVP（最小可用版本）
2. 将非核心功能移到下一个版本
3. 确保 MVP 版本的 commit 列表自洽
```

### 场景 4：开发中发现方案不可行

```
已经开发到一半，发现技术方案有根本性问题
修正：
1. 停止当前开发
2. 记录问题和已尝试的方案
3. 回到 Step 2 重新设计
4. 重新拆分 commit（从当前进度开始）
5. 已完成的 commit 不需要回滚（除非有 bug）
```
